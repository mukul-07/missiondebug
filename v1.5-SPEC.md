# MissionDebug v1.5 — Build Specification

## Context

v1 shipped six phases and proved the record → detect → replay loop end-to-end:
two built-in detectors (stall, path-deviation), `.deb` install, annotations,
shareable URLs, fixture-driven onboarding. Acceptance was a 30-day
design-partner trial.

But v1's two hardcoded detectors only fit a narrow slice of robots — ones
where stall and path deviation are the dominant failure modes. **Most
real robots have different anomalies.** A drone cares about altitude
deviation and motor RPM divergence. A surgical arm cares about force
exceedance during contact. A picking robot cares about gripper slip and
object misdetection. Hardcoding detectors per customer is the wrong shape:
each customer needs 3-5 of *theirs* in week one, and we'd be writing Python
forever.

**v1.5 turns MissionDebug from an opinionated tool into a topic-agnostic
configurable framework.** The customer reads their own robot's ROS topic
list, picks the topics that change meaningfully during failures, and
writes YAML rules that say "fire when this topic's this field meets this
condition for this duration." The agent honors the rules without us
shipping new code per customer.

The system never tries to *guess* what an anomaly is. It gives the user
the language to *tell* it. Robotics anomalies are deeply domain-specific
and the customer knows them better than we do.

### Why config-driven detectors

A robot can have ~45 distinct anomaly types if you decompose them strictly
across six domains (locomotion, perception, planning, localization, behavior,
hardware). Mature fleets monitor **5–15** at any time; ~8 cover most failure
modes most teams care about (stall, collision, sensor dropout, planning
failure, localization loss, FSM error, battery low, e-stop). The remaining
30+ are deeply customer-specific.

Hardcoding even the common 8 in Python is the wrong shape — every customer
needs 3-5 of *theirs* added in week one. v1.5 inverts the model: ship the
**rule framework** plus pattern templates, let customers compose their own
detectors. One Python detector module supports thousands of deployed rules
across thousands of different robot schemas.

### How the user actually uses it

Three modes, none requiring us to know the customer's robot:

1. **User writes rules in YAML.** Topic name, field path, condition,
   duration. No Python, no plugins. Works for any topic of any message
   type the agent can subscribe to.
2. **User hits a button (or curl).** `POST /sessions/save` captures the
   last 60s. For anomalies that don't fit a rule, or for ad-hoc forensics.
3. **User's existing monitoring fires.** Prometheus, custom watchdogs,
   mission software — anything they already have detecting problems can
   POST to MissionDebug instead of writing a new rule.

v1.5 ships the framework for #1. #2 and #3 already work in v1.

### Positioning vs existing tools

For customers with a continuous bag-recording system already in place
(rolling N-second files, e.g. one common pattern is a per-shift bag manager
that triggers on a single state-topic error), MissionDebug deploys
**alongside, not as replacement.** Their existing tool keeps the deep
archive of high-volume topics (point clouds, costmaps, raw sensor
streams). MissionDebug owns the focused, RAM-buffered, replay-ready layer
for the small set of topics engineers actually scrub during incidents.
Two layers, complementary, no rip-and-replace.

## What v1.5 IS

- **Topic-agnostic rule engine.** YAML schema for `state_equality` and
  `numeric_threshold` rules over any ROS message field. Same `update +
  duration + cooldown` discipline as v1's hardcoded detectors.
- **Configurable per-topic capture.** Each topic gets its own ring window
  (`ring_seconds`) and optional rate-limiter (`rate_divisor`) so cameras,
  lidars, and high-rate diagnostics can coexist without busting the RAM
  budget. Global byte cap as backstop.
- **Disk retention.** Backend deletes oldest sessions when total size
  exceeds a configurable cap. Sessions can run unattended for weeks.
- **Backend + web `.deb`s.** All three services install via `dpkg`. Customer
  goes from `apt`-style install to running in <60 seconds, no source tree.
- **Two built-in convenience detectors.** `topic_dropout` (silence on a
  watched topic) and `battery_low` (a typed wrapper over numeric_threshold
  for `BatteryState.percentage`). Demonstrate the framework; customers
  add the rest in YAML.
- **Examples for multiple robot profiles.** Reference configs and rule
  packs covering at least three robot archetypes — ground vehicle,
  drone, manipulator — so a new customer sees their domain reflected.

## What v1.5 IS NOT

- Not a Python plugin system for custom detector code. Config-driven only.
  Custom detector code is v2.
- Not multi-robot UI. One robot per browser tab. Fleet view is v2.
- Not cloud-hosted, not authenticated. Network-level trust.
- Not new visualization panels (lidar, point cloud, costmap, joint state).
  Those data are captured for replay in Foxglove; UI rendering is v2.
- Not a Rust agent rewrite.
- Not search across sessions.
- Not live streaming.
- Not native protocol decoders for industry standards (VDA 5050, ROS 2
  control, etc.). Customer publishes status as topics; we capture topics.
- Not a guess engine. We don't infer anomalies the customer didn't tell
  us about.

If a feature is not explicitly listed in "v1.5 IS", it does not exist in v1.5.
Same discipline as v0/v1.

## Tech Stack (delta from v1)

Everything in v1 stays. Additions:

### Agent
- New `detectors/from_config.py` — loads rule-based detectors from YAML.
  Two rule kinds:
  - `state_equality` — fires when `field == value` (or `!=`) for ≥ duration
  - `numeric_threshold` — fires when `field` satisfies `<`, `>`, `<=`, `>=`
    for ≥ duration
- New built-ins (still in `detectors/`): `battery_low.py`, `topic_dropout.py`.
- New `decoder.py` — minimal CDR field walker so rules can read named
  fields (incl. nested like `status.status`) without fully deserializing
  the whole ROS message tree.
- Per-topic config: `{ name, type, rate_divisor: int = 1, ring_seconds: float | None }`
  where `rate_divisor=10` means capture every 10th message.

### Backend
- New retention task: every 60s, sums `mcap_size_bytes` across sessions; if
  total > `MD_MAX_DISK_MB`, deletes oldest first. Annotation rows
  cascade-delete via the existing FK.
- One new endpoint: `GET /api/admin/disk` returns total bytes + count.

### Packaging
- `make package` produces three .debs: `missiondebug-agent`,
  `missiondebug-backend`, `missiondebug-web`. systemd units for all three.

### Frontend
- Session list shows the rule label (e.g. `anomaly:fsm-error`,
  `anomaly:altitude-deviation`), not just `anomaly:stall` /
  `anomaly:path-deviation`.
- (No new panels.)

## Build Plan — Phased

### Phase 1 — Configurable buffer + selective topic capture (target: 1 day)

1. Extend `TopicConfig` with optional `rate_divisor: int = 1` and
   `ring_seconds: float | None` (None = use global default).
2. Ring buffer becomes a *map* of per-topic deques. Each topic evicts
   on its own window. Total RAM cap enforced by a global byte budget;
   when exceeded, oldest entries across all topics drop until under cap.
3. Update `ros_bridge.py`: skip every Nth message per topic if
   `rate_divisor > 1`.
4. Tests: per-topic eviction, global budget, rate-limiting, mixed.

Deliverable: any robot's topic list — including high-rate cameras, lidars,
or diagnostics — can be configured to fit a defined RAM budget.

### Phase 2 — Generic config-driven detectors (target: 2 days)

1. New `decoder.py`: read a single named field (with dot-paths for nested,
   e.g. `status.status`) from a ROS message bytes-blob using lazy CDR
   walk. Skip rest of the message.
2. `detectors/from_config.py` loads rules:
   ```yaml
   anomaly:
     rules:
       - name: my-state-anomaly
         topic: /any/topic/the/robot/publishes
         field: any.dotted.field.path
         equals: "value"               # or not_equals, lt, gt, lte, gte
         duration_seconds: 5
         cooldown_seconds: 30
   ```
3. Same `update + cooldown` discipline as the existing detectors. Reuses
   the anomaly-fired callback path that triggers a save.
4. Tests:
   - state-equality: fires after duration, resets on field change, cooldown
     blocks re-fire
   - numeric-threshold: same, plus boundary cases
   - dotted field paths through nested messages
   - missing field handled gracefully (warn once, then silent)
   - multiple rules on the same topic don't interfere

Deliverable: replay any pre-recorded MCAP through the agent with a custom
rule set; observe rules firing exactly when their conditions match.

### Phase 3 — Topic-dropout + battery-low built-ins (target: 0.5 day)

1. `topic_dropout.py` — fires when no message on a watched topic for >
   `silence_seconds`. Useful for "sensor died" signal that no rule on
   message *contents* can express.
2. `battery_low.py` — wrapper over numeric_threshold for
   `sensor_msgs/msg/BatteryState.percentage`. Nicer config syntax.
3. Tests for both.

Deliverable: dropout fires when a publisher is killed mid-flow.

### Phase 4 — Disk retention + size cap (target: 0.5 day)

1. Backend background task (next to the rescan loop): every 60s, query
   total bytes in DB. If > `MD_MAX_DISK_MB` (default 100 GB), delete
   oldest sessions until under cap.
2. Endpoint `GET /api/admin/disk` returns `{total_bytes, count, cap_bytes}`.
3. Test: insert N fake sessions, set cap below sum, run retention, verify
   oldest deleted in order.

Deliverable: agent + backend can run unattended for weeks without the
sessions dir filling the disk.

### Phase 5 — Backend + web packaging (target: 2 days)

1. `packaging/debian/backend/` and `packaging/debian/web/` skeletons.
2. Backend systemd unit, runs as `missiondebug` user, reads from
   `/var/lib/missiondebug/sessions/`.
3. Web: `pnpm build` produces a static dist; .deb installs under
   `/opt/missiondebug-web/` and registers a small static-server systemd
   unit on port 8080.
4. `make package` builds all three .debs into `dist/`.

Deliverable: on a fresh Ubuntu 22.04:
```bash
sudo dpkg -i dist/*.deb
# Three services running, browser at http://robot.local:8080 shows the UI
```

### Phase 6 — Generic fixture + cross-robot examples + docs (target: 1.5 days)

1. `fixtures/synthetic_drive.mcap` — generic 60s session that exercises
   the rule engine: a status field flips to `"error"`, a numeric field
   crosses a threshold, a topic stops publishing. **Not robot-specific.**
2. `examples/ground-vehicle-config.yaml` — AGV/forklift/rover archetype
   showing the tiered topic strategy and 3-5 rule examples.
3. `examples/drone-config.yaml` — quadrotor archetype with rules for
   altitude deviation, battery, GPS loss, motor RPM divergence.
4. `examples/manipulator-config.yaml` — arm/picker archetype with rules
   for grip force, joint limit, contact-detection failure.
5. `examples/rule-patterns.yaml` — copy-paste rule TEMPLATES, not
   pre-baked rules. Each comes with a comment explaining the *pattern*
   (equality on a state topic, threshold on a numeric field, dropout
   on a sensor) and a customer can search/replace topic + field + value.
6. `examples/README.md` — "Pick the archetype closest to your robot.
   Copy. Replace topic names. Restart the agent."
7. README updated with rule schema reference and link to examples.
8. v1.5 release notes.

Deliverable: fresh clone → `make install` → `MD_FIXTURES=1 make dev`
shows the synthetic session with multiple fired anomalies. The
`examples/` directory gives any new customer — regardless of robot type
— a working starting point they can adapt in <30 minutes.

## Hard Rules — DO NOT DEVIATE

The v0 ten + v1's three still apply. Three new ones:

14. **Config-driven detectors must NOT load arbitrary Python.** Only the
    two rule kinds (`state_equality`, `numeric_threshold`) plus their
    built-in convenience wrappers. If a customer needs custom logic,
    that's v2's plugin system. Don't compromise the agent's security
    posture for one customer's edge case.
15. **Per-topic ring buffers don't share a deque.** Each topic gets its
    own. A burst of camera frames must not evict state-topic history.
16. **Retention is a backend concern, not the agent's.** The agent writes
    files freely. Only the backend's lifespan task deletes them. Single
    writer, single deleter — no race between agent saves and retention.

## Non-Functional Requirements (delta from v1)

- Agent CPU during recording: still <2% on a Jetson Orin Nano *with the
  customer's actual topic config*. If exceeded, customer applies
  `rate_divisor` until it fits. We provide the knob, customer tunes.
- Agent RAM: <500 MB total (raised from v0's 200 MB) for a typical
  10-15 topic config with 60s buffers. Configurable global cap.
- Detector evaluation: <1ms per message on a typical robot CPU.
- Retention task: must hold the GIL for <100ms per cycle so the FastAPI
  event loop stays responsive.

## Acceptance Test (must pass before v1.5 is "done")

The test has two halves: technical (the framework works) and field-validated
(a real partner runs it).

### Technical
1. The rule engine handles, in tests, every rule kind documented in
   `examples/rule-patterns.yaml` against synthetic data.
2. All three .debs install on a fresh Ubuntu 22.04 in <60 seconds total.
3. 14 days of synthetic load: agent + backend run unattended, retention
   keeps disk under cap, no crashes.
4. All v1 tests still green; new tests for rule engine, retention,
   per-topic buffer.

### Field
5. **At least one real robotics team installs v1.5** on their actual
   robot, configures their own topic list and rule set (not from our
   examples — their rules), and runs unattended for 14 days. No
   engineering visits, no source pulls.
6. Day-14 verdict from the partner:
   - **"This earns its place in our debug stack"** → v1.5 is done.
     Pricing conversation begins.
   - **"It works but we'd want X before deploying to more robots"** → X
     is v1.5.5 scope; iterate. v1.5 is done in spirit.
   - **"It crashed / lost data / wasted disk"** → v1.5 has a bug. Fix
     it and re-run.

The verdict to *avoid*: "this would be a great bag-manager replacement
if you added Y." That's a sign the engineer pushed v1.5 toward replacement
when the spec was complementary. Pull back. Replacement is v2 territory.

The technical box-checks are necessary but not sufficient. **The
customer's verdict is the test.**

## Out of Scope (explicit v2 list)

- Multi-robot fleet view + per-robot health dashboard
- Search across sessions
- Cloud sync (opt-in upload of selected sessions)
- Auth (single shared password gating the UI)
- Python plugin system for custom detectors
- Rule kinds beyond `state_equality` and `numeric_threshold`
  (e.g. rate-of-change, statistical, cross-topic correlations)
- 3D pose viewer + URDF rendering
- Lidar / point cloud / costmap visualization panels
- Live streaming
- Comparison view (this run vs baseline)
- Video transcoding to HLS
- Mobile responsive UI
- Foxglove deep-link export
- Rust agent rewrite
- Native protocol decoding (VDA 5050, ROS 2 control, etc.)
- MCP server integration
- Customer billing
- Helm chart / Kubernetes
- RBAC / SAML / SSO

All of the above are real and useful. None of them block any reasonable
robotics team from deploying v1.5 today. They earn priority by customers
asking, not by us guessing.

## How to Use This Spec

Same as v0/v1:
1. Implement Phase N. Stop at the deliverable. Commit.
2. Don't start N+1 until N's deliverable test passes.
3. Reject in-phase scope creep with: "that's v2."

If a design partner asks during the cycle for something not in this spec,
write it down — that's v1.5.5 input — but don't insert it. The 14-day
trial needs a fixed target.

## What this spec costs

~7.5 working days, real-time. Same risk profile as v1: one engineer, focused.

If v1.5 lands and a real partner says yes, **the framework is the product
from then on.** Topic-rule detectors, three-package install, disk retention,
multi-robot examples — those are the talking points for any future
customer regardless of robot type. v2's job stops being "prove the idea"
and becomes "make the framework richer" (more rule kinds, plugin system,
fleet view, cloud sync).
