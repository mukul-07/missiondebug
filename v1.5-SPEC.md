# MissionDebug v1.5 — Build Specification

## Context

v1 shipped six phases and proved the record → detect → replay loop end-to-end:
two built-in detectors (stall, path-deviation), .deb install, annotations,
shareable URLs, fixture-driven onboarding. The acceptance test was a 30-day
design-partner trial.

v1.5 is **scoped to one specific design partner** — an autonomous forklift
operator running ~70 topics on each robot via a `bag_manager` config. They
already validated the pattern (continuous 300-second rolling bags moved to an
`error/` folder when their FSM enters an error state for ≥ 40s). MissionDebug
v1's two detectors covered ~10% of the failure surface they care about.

v1.5's job is to close the gap so they can actually deploy MissionDebug to
replace (or run alongside) their bag-manager.

## What v1.5 IS

- **Generic, config-driven detectors.** No more hardcoded Python per detector.
  Customer writes YAML rules like "fire when `/robot_state_fms.state == 'error'`
  for ≥ 40s" and the agent honors them.
- **Configurable ring buffer.** Length per-topic, max RAM cap, optional
  per-topic rate-limiting (every Nth message) so cameras + lidars + diagnostics
  don't blow the budget.
- **Disk retention.** Backend deletes oldest sessions when total size exceeds
  a configurable cap (matching the bag-manager's `MaxFolderSize`).
- **Backend + web `.deb`s.** Customer installs three packages on one box,
  starts three services, opens a browser. No `make dev` from source.
- **Two new built-in detectors** seeded for common patterns: battery-low,
  topic-dropout. Enough to demonstrate the framework; rest are config.
- **Real customer-shaped fixture.** A 60s synthetic forklift session with
  their topic names so the demo speaks their language.

## What v1.5 IS NOT

- Not multi-robot UI. One robot per browser tab. (Customer has many robots
  but switches between URLs for now — they're not asking for unified view yet.)
- Not cloud-hosted, not authenticated. Network-level trust.
- Not a Python plugin system for custom detector code. Config-driven only.
  Custom detectors come in v2.
- Not new visualization panels (lidar, point cloud, costmap, joint state).
  Those data are captured for replay in Foxglove; UI rendering is v2.
- Not Rust agent rewrite.
- Not search across sessions.
- Not live streaming.
- Not VDA 5050 native protocol support. (Customer publishes VDA state on a
  topic; we capture it as a topic. That's enough.)

If a feature is not explicitly listed in "v1.5 IS", it does not exist in v1.5.
Same discipline as v0/v1.

## Tech Stack (delta from v1)

Everything in v1 stays. Additions:

### Agent
- New `detectors/from_config.py` — loads rule-based detectors from YAML.
- Two rule kinds:
  - `state_equality` — fires when `field == value` for ≥ duration
  - `numeric_threshold` — fires when `field` is `<`, `>`, `<=`, `>=` a value
    for ≥ duration
- New built-ins (still in `detectors/`): `battery_low.py`, `topic_dropout.py`.
- Per-topic config: `{ name, type, rate_divisor: int, ring_seconds: float }`
  where rate_divisor=1 means capture all, =10 means every 10th.

### Backend
- New retention task: every 60s, sums `mcap_size_bytes` across sessions; if
  total > `MD_MAX_DISK_MB`, deletes oldest first.
- One new endpoint: `GET /api/admin/disk` returns total bytes + count.

### Packaging
- `make package` produces three .debs: `missiondebug-agent`, `missiondebug-backend`,
  `missiondebug-web`. Install with one apt command. systemd units for all three.

### Frontend
- Session list shows the rule label (e.g. `anomaly:fsm-error`), not just
  `anomaly:stall` / `anomaly:path-deviation`.
- (No new panels.)

## Build Plan — Phased

### Phase 1 — Configurable buffer + selective topic capture (target: 1 day)

1. Extend `TopicConfig` with optional `rate_divisor: int = 1` and
   `ring_seconds: float | None` (None means use global default).
2. Ring buffer becomes a *map* of per-topic deques. Eviction uses each
   topic's own window. Total RAM cap enforced by a global byte budget.
3. Update `ros_bridge.py`: skip every Nth message per topic if rate_divisor > 1.
4. Tests: per-topic eviction, global budget, rate-limiting.

Deliverable: customer's `bag_manager_config.yaml` topic list works on a
typical robot CPU + RAM target without exceeding the v0 NFRs.

### Phase 2 — Generic config-driven detectors (target: 2 days)

1. New `decoder.py` that reads a single named field from a serialized ROS
   message bytes-blob without fully deserializing the whole message
   (lazy CDR field walk).
2. `detectors/from_config.py` loads rules:
   ```yaml
   anomaly:
     rules:
       - name: fsm-error
         topic: /mag_fl_003/robot_state_fms
         field: state
         equals: "error"
         duration_seconds: 40
         cooldown_seconds: 60
       - name: low-battery
         topic: /mag_fl_003/bms_feedback
         field: percentage
         lt: 0.20
         duration_seconds: 5
         cooldown_seconds: 600
       - name: lidar-safety-tripped
         topic: /mag_fl_003/lidar_safety_status
         field: tripped
         equals: true
         duration_seconds: 0
         cooldown_seconds: 30
   ```
3. Same `update + cooldown` discipline as the existing detectors. Reuses the
   anomaly-fired callback path.
4. Tests: state-equality fires/resets/cooldowns; numeric-threshold likewise;
   missing-field handled gracefully; multiple rules on the same topic.

Deliverable: replay a recorded forklift bag through the agent with these
three rules and see exactly the events their old bag-manager would have
flagged.

### Phase 3 — Topic-dropout + battery-low built-ins (target: 0.5 day)

1. `topic_dropout.py` — fires when no message on a watched topic for >
   `silence_seconds`. Useful for sensor failure ("haven't heard from the
   front lidar in 10s — capture the previous minute").
2. `battery_low.py` — convenience wrapper around the numeric-threshold rule
   for `sensor_msgs/msg/BatteryState.percentage`. Just nicer config syntax.
3. Tests for both.

Deliverable: dropout fires when a publisher is killed mid-flow.

### Phase 4 — Disk retention + size cap (target: 0.5 day)

1. Backend background task (next to the rescan loop): every 60s, query
   total bytes in DB. If > `MD_MAX_DISK_MB` (default 100 GB), delete
   oldest sessions until under cap. Annotation rows cascade-delete.
2. Endpoint `GET /api/admin/disk`.
3. Test: insert 5 fake sessions, set cap to size-of-3, run retention,
   verify oldest 2 vanish.

Deliverable: agent + backend can run unattended for weeks without the
sessions dir filling the disk.

### Phase 5 — Backend + web packaging (target: 2 days)

1. `packaging/debian/backend/` and `packaging/debian/web/` skeletons.
2. Backend systemd unit, runs as `missiondebug` system user, reads from
   `/var/lib/missiondebug/sessions/` (and optionally `/var/lib/missiondebug/fixtures/`).
3. Web: `pnpm build` produces a static dist; the .deb installs it under
   `/opt/missiondebug-web/` and registers a tiny `nginx`-or-`caddy`-or-stdlib
   static server systemd unit on port 8080.
4. `make package` builds all three .debs into `dist/`.

Deliverable: on a fresh Ubuntu 22.04:
```bash
sudo dpkg -i dist/*.deb
# Three services running, browser at http://robot.local:8080 shows the UI
```

### Phase 6 — Real customer-shaped fixture + docs (target: 1 day)

1. `fixtures/forklift_drive.mcap` — synthetic 60s "forklift" with `cmd_vel`,
   pose, planned path, AND populated FSM, battery, lidar-safety topics so
   each rule-based detector can fire on it.
2. README updated: configure the new rule schema, link to the example.
3. v1.5 release notes.

Deliverable: fresh clone → `make install` → `MD_FIXTURES=1 make dev` shows
a session containing a fired `fsm-error`, `low-battery`, AND `lidar-safety-tripped`
anomaly. Customer sees their own concepts on screen.

## Hard Rules — DO NOT DEVIATE

The v0 ten + v1's three still apply. Three new ones:

14. **Config-driven detectors must NOT load arbitrary Python.** Only the two
    rule kinds (`state_equality`, `numeric_threshold`). If a customer needs
    custom logic, that's v2's plugin system. Don't compromise the agent's
    security posture for one customer's edge case.
15. **Per-topic ring buffers don't share a deque.** Each topic gets its own.
    A burst of camera frames must not evict /robot_state_fms history.
16. **Retention is a backend concern, not the agent's.** The agent writes
    files freely. Only the backend's lifespan task deletes them. Single
    writer, single deleter — no race between agent saves and retention.

## Non-Functional Requirements (delta from v1)

- Agent CPU during recording: still <2% on a Jetson Orin Nano, *with the
  customer's 70-topic config* (validated against this design partner).
  If exceeded, rate_divisor on point clouds/costmaps until it fits.
- Agent RAM: <500 MB total (raised from v0's 200 MB) for the customer
  topic set with 60s buffers. Configurable global cap.
- Detector evaluation: <1ms per message on the customer's hardware.
- Retention task: must hold the GIL for <100ms per cycle so the FastAPI
  event loop stays responsive.

## Acceptance Test (must pass before v1.5 is "done")

The same shape as v1: one customer, real deployment, real time.

1. The forklift design partner installs all three .debs on **one robot**
   via `dpkg -i`, no source tree present.
2. They configure `/etc/missiondebug/config.yaml` with their actual topic
   list and at least three rule-based detectors.
3. **They run it for 14 days unattended.** No engineering visits. No source
   pulls.
4. Day-14 verdict from the partner:
   - **"This replaces our bag-manager"** → v1.5 is done. Pricing
     conversation begins.
   - **"It works but bag-manager still wins on X"** → that X is v1.5.5
     scope; iterate. v1.5 is done in spirit.
   - **"It crashed / lost data / wasted disk"** → v1.5 has a bug. Fix it
     and re-run.

The technical box-checks (3 .debs install, retention works, rules fire) are
necessary but not sufficient. **The customer's verdict is the test.**

## Out of Scope (explicit v2 list)

- Multi-robot fleet view + per-robot health dashboard
- Search across sessions
- Cloud sync (opt-in upload of selected sessions)
- Auth (single shared password gating the UI)
- Python plugin system for custom detectors
- 3D pose viewer + URDF rendering
- Lidar / point cloud / costmap visualization panels
- Live streaming
- Comparison view (this run vs baseline)
- Video transcoding to HLS
- Mobile responsive UI
- Foxglove deep-link export
- Rust agent rewrite
- VDA 5050 native protocol decoding (we capture, not interpret)
- MCP server integration
- Customer billing
- Helm chart / Kubernetes
- RBAC / SAML / SSO

All of the above are real and useful. None of them block this design partner
from deploying v1.5 today. They earn priority by customers asking, not by us
guessing.

## How to Use This Spec

Same as v0/v1:
1. Implement Phase N. Stop at the deliverable. Commit.
2. Don't start N+1 until N's deliverable test passes.
3. Reject in-phase scope creep with: "that's v2."

If the design partner asks during the cycle for something not in this spec,
write it down — that's v1.5.5 input — but don't insert it. The 14-day trial
needs a fixed target.

## What this spec costs

~7 working days, real-time. Same risk profile as v1: one engineer, focused.

If v1.5 lands and the customer says yes, **that's the second customer pitch
ready.** Topic-rule detectors, three-package install, disk retention, customer-
shaped fixture — those are ready-made talking points for the next robotics
team. v2's job is no longer "prove the idea" but "make it broadly applicable."
