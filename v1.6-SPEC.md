# MissionDebug v1.6 — Build Specification

## Context

v1.5 inverted the model: instead of shipping detectors per customer, we shipped
a YAML rule framework with two kinds (`state_equality`, `numeric_threshold`)
and let customers compose their own. Two convenience built-ins (`topic_dropout`,
`battery_low`) demonstrated the shape. The spec was deliberate about scope:
*"We don't infer anomalies the customer didn't tell us about."*

v1.5's two rule kinds cover the static cases — *"is this field equal to that
value"*, *"is this field above that number"*. They miss two large classes of
real anomalies:

1. **Anomalies defined by motion, not state.** A battery sitting at 60% is
   fine; a battery dropping from 80% to 60% in thirty seconds is a thermal
   runaway. An IMU bias drifting steadily means a sensor is dying long before
   it crosses any hard limit. v1.5 has no way to express "changed by X over
   Y seconds."
2. **Anomalies that only exist as a conjunction.** *"Commanded velocity > 0.5
   m/s AND wheel odometry < 0.05 m/s"* is a stall that neither topic alone
   can describe. v1.5's rules each watch one topic; there's no way to say
   "fire when A and B hold simultaneously."

Both are pure extensions of the rule framework, not new architecture. They
slot in next to the existing two `kind`s in `from_config.py`, reuse the same
`update + duration + cooldown` discipline, and stay inside Hard Rule 14
(no arbitrary Python).

**v1.6 adds two rule kinds — `rate_of_change` and `cross_topic` — and nothing
else.** It is a deliberate small release: ship the two highest-leverage
extensions to the framework v1.5 proved out, then let the field decide what
v2 should be.

### Why these two, why now

The v1.5 spec is explicit that v2 priorities should be customer-pulled, not
guessed. That argues against fleet-view, cloud-sync, plugin-system — all of
which lock in big architectural bets a real partner might invalidate.

Rate-of-change and cross-topic are different. They:

- extend the framework along its existing grain (same YAML, same loader,
  same anomaly callback),
- compose with each other and with the existing two kinds (a cross-topic rule
  whose sub-conditions are themselves rates-of-change covers differential-drive
  imbalance, accelerometer-vs-IMU divergence, planner-vs-localizer drift),
- take the rule framework from "covers static thresholds" to "covers most of
  what mature monitoring stacks express in PromQL" — without giving up the
  config-only security posture.

If v1.5 lands a partner and they ask for one of these, we have it. If they
ask for fleet-view instead, v1.6 still made the framework strictly more
expressive at low cost. Low-regret bet.

## What v1.6 IS

- **`rate_of_change` rule kind.** Fires when a numeric field's change over a
  sliding window crosses a threshold. Two flavors: `delta_gt` / `delta_lt`
  (absolute change over the window) and `rate_gt` / `rate_lt` (per-second
  slope). Same `duration + cooldown` gate as v1.5 rules.
- **`cross_topic` rule kind.** Fires when a conjunction (`when_all`) or
  disjunction (`when_any`) of per-topic field conditions holds. Each
  sub-condition reuses the v1.5 comparator vocabulary (`equals`,
  `not_equals`, `lt`, `gt`, `lte`, `gte`). Per-sub-condition `max_age_seconds`
  prevents firing on a frozen reading from a topic that stopped publishing.
- **Composition.** A `cross_topic` sub-condition may itself be a
  `rate_of_change` check. No new syntax — sub-conditions accept the same
  shape the top-level rule loader already understands.
- **Examples updated.** The three archetype configs (`ground-vehicle`,
  `drone`, `manipulator`) each gain at least one rate-of-change and one
  cross-topic rule that's idiomatic for that archetype. `rule-patterns.yaml`
  gains template entries for both new kinds.

## What v1.6 IS NOT

- Not statistical rules (mean, stddev, percentile windows). Useful, but
  one step further from the static-threshold mental model — defer until a
  customer asks.
- Not cross-topic *correlations* in the statistical sense (Pearson, lag
  estimation). v1.6's "cross-topic" is just AND/OR over per-topic conditions.
- Not a Python plugin system. Hard Rule 14 from v1.5 still binds.
- Not new UI. Session list already shows the rule label; new kinds inherit.
- Not new packaging. v1.5's three .debs absorb the change.
- Not a query language. Rules stay declarative YAML; no expressions, no
  arithmetic, no derived fields. If a customer needs `(a - b) / c`, they
  publish that as a topic.

If a feature is not explicitly listed in "v1.6 IS", it does not exist in v1.6.
Same discipline as v0/v1/v1.5.

## Tech Stack (delta from v1.5)

Everything in v1.5 stays. Additions are confined to one file plus tests.

### Agent
- `detectors/from_config.py` gains two new `kind` branches:
  - `rate_of_change` — per-rule ring of `(monotonic_t, value)` samples
    trimmed to `window_seconds`. On each update, compute oldest-vs-newest
    delta (and / or slope = delta / actual elapsed), evaluate against
    `delta_gt` / `delta_lt` / `rate_gt` / `rate_lt`. Sample ring is
    bounded by `window_seconds`, not message count, so a high-rate topic
    doesn't blow memory — drop intermediate samples once the window has
    ≥ `max_samples` (default 256) entries via uniform decimation.
  - `cross_topic` — each sub-condition keeps `(latest_value, latest_t)`
    pulled from its topic's most recent decoded message. The rule
    subscribes (logically) to *every* topic named in its sub-conditions
    and re-evaluates the whole conjunction on *any* contributing update.
    A sub-condition whose `latest_t` is older than its `max_age_seconds`
    is treated as "unknown" — `when_all` does NOT fire (conservative);
    `when_any` ignores it.
- No change to `decoder.py` (already returns `(value, t)`).
- No change to `ros_bridge.py` subscription logic — `from_config.py`
  declares the union of topics it needs the same way it does today.

### Backend / Frontend / Packaging
- No changes. Rule labels flow through unchanged.

## Build Plan — Phased

### Phase 1 — `rate_of_change` rule kind (target: 1 day)

1. Extend the rule loader to recognize `kind: rate_of_change` with fields
   `topic`, `field`, `window_seconds`, one of `delta_gt|delta_lt|rate_gt|rate_lt`,
   plus the standard `duration_seconds` / `cooldown_seconds`.
2. Per-rule sample ring keyed by monotonic time. On update: trim to
   `window_seconds`, decimate if over `max_samples`, evaluate.
3. Reuse the existing fire/duration/cooldown machinery — same callback path.
4. Tests:
   - `delta_gt` fires when absolute change exceeds threshold; doesn't fire
     when change is within threshold.
   - `rate_gt` correct against synthetic linear ramps.
   - Window trimming: an old big delta scrolls out and stops firing.
   - Empty window / single sample: graceful (no fire, no crash).
   - Decimation under high rate: result within tolerance of un-decimated.

Deliverable: replay an MCAP where battery drops 20% in 30s; rule fires once,
honors cooldown.

### Phase 2 — `cross_topic` rule kind (target: 1.5 days)

1. Loader recognizes `kind: cross_topic` with `when_all` or `when_any` (exactly
   one), each containing a list of sub-conditions in v1.5's existing per-topic
   shape, each gaining an optional `max_age_seconds`.
2. Sub-condition state: `(latest_value, latest_t, last_eval)`. Updated on each
   matching message via the same decoder path.
3. Re-evaluate the whole rule on any contributing topic's update. Stale
   sub-conditions (`now - latest_t > max_age_seconds`) count as unknown.
4. Tests:
   - `when_all` fires only when both sub-conditions hold simultaneously.
   - `when_any` fires when either holds.
   - Stale sub-condition: `when_all` does not fire; `when_any` ignores it
     and fires on the live one.
   - Sub-condition that is itself a `rate_of_change` works (composition).
   - Two cross-topic rules sharing a topic don't interfere.

Deliverable: replay an MCAP with `/cmd_vel.linear.x > 0.5` and
`/odom.twist.twist.linear.x < 0.05` overlapping for 3s; rule fires once.

### Phase 3 — Examples + docs (target: 0.5 day)

1. `ground-vehicle-config.yaml` — add a "commanded-but-not-moving" cross-topic
   stall rule and a "wheel-current-spike" rate-of-change rule.
2. `drone-config.yaml` — add a "battery-draining-fast" rate-of-change rule and
   an "altitude-vs-throttle-divergence" cross-topic rule.
3. `manipulator-config.yaml` — add a "joint-velocity-spike" rate-of-change
   rule and a "force-with-no-contact" cross-topic rule.
4. `rule-patterns.yaml` — copy-paste templates for both kinds, each with a
   one-paragraph comment on the *pattern* (slope-over-window; conjunction
   with staleness guard).
5. README rule schema reference updated; v1.6 release notes.

Deliverable: a customer reading `examples/` sees rate-of-change and
cross-topic rules in their archetype, can copy and edit by topic name
in <10 minutes.

## Hard Rules — DO NOT DEVIATE

The v0 ten + v1's three + v1.5's three still apply. One new one:

17. **Rule kinds must remain pure functions of buffered message state.** No
    rule kind in v1.6 (or v2) may make network calls, read files, exec
    subprocesses, or import modules at evaluation time. The rule loader
    decides everything at config-load; the hot path only reads decoded fields
    and timestamps. This is how we keep "<1ms per message" honest and how
    config stays safe to share.

## Non-Functional Requirements (delta from v1.5)

- `rate_of_change` evaluation: <1ms per message including ring trim and
  decimation, on a typical robot CPU. Verify with a 100Hz synthetic stream.
- `cross_topic` evaluation: <1ms per re-eval, irrespective of how many
  sub-conditions a rule has (within reason — cap at 8 sub-conditions per
  rule; reject configs with more at load time).
- Per-rule sample ring: bounded by `max_samples` (default 256). A 60s window
  on a 100Hz topic decimates to ~4Hz worth of stored samples; slope error
  under 1% for monotone signals.
- No change to agent CPU / RAM envelopes from v1.5.

## Acceptance Test (must pass before v1.6 is "done")

### Technical
1. New tests in `test_rate_of_change.py` and `test_cross_topic.py` all green;
   all v1.5 tests still green.
2. Each archetype example loads cleanly, all rules parse, agent starts.
3. The synthetic fixture (or a v1.6 addition to it) demonstrates one
   rate-of-change firing and one cross-topic firing in the same session.
4. Soak test: 1 hour of synthetic 100Hz traffic through a config with 5
   rate-of-change + 5 cross-topic rules, agent CPU within v1.5 envelope.

### Field
5. **At least one v1.5 user adopts a v1.6 rule kind in production.** The
   verdict to look for: *"the rate-of-change rule caught X that we'd been
   missing"* or *"the cross-topic rule replaced a custom watchdog we were
   maintaining."* Either confirms the framework now covers a class of
   anomaly v1.5 couldn't.

The verdict to *avoid*: *"we'd want statistical / cross-correlation /
expression rules."* That's evidence v1.7 should keep extending the rule
vocabulary, not that v1.6 was wrong — but it does mean v1.6 alone isn't
enough for that user. Note it; don't insert it into v1.6.

## Out of Scope (explicit v1.7+ list)

Carries forward from v1.5's v2 list, plus:

- Statistical rules (rolling mean, stddev, percentile thresholds)
- Cross-topic statistical correlations (Pearson, lag-estimated)
- Expression / arithmetic rules (`(a - b) / c > k`)
- Derived / virtual topics computed from other topics
- Per-rule custom labels routed to different storage destinations
- Rule hot-reload (today: restart agent to pick up config changes)

## How to Use This Spec

Same as v0/v1/v1.5:
1. Implement Phase N. Stop at the deliverable. Commit.
2. Don't start N+1 until N's deliverable test passes.
3. Reject in-phase scope creep with: "that's v1.7."

## What this spec costs

~3 working days, real-time. Smaller than v1.5 by design — v1.6 is a focused
extension of a framework that already works, not new architecture.

If v1.6 lands and a v1.5 user reaches for one of the new kinds without
prompting, the rule framework has crossed from "covers the easy cases" to
"covers most of what real monitoring expresses." That's the threshold where
v2 conversations stop being about adding rule kinds and start being about
the things v1.5 deferred — fleet view, cloud sync, plugin system — driven
by which one a paying customer asks for first.
